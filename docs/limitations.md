# 解釈上の制約と条件変更

## 成績の対象

固定20課題のうち19課題171試行を採点し、build-cython-extの9試行は保留です。oracle自体が2回10/11合格で、下位pyknotidの`test_reconstructed_space_curve`が`KeyError: pos`を起こしました。planarity 1.0.0/networkx 3.7のAPI互換性が候補ですが原因版は未分離。元課題/解答/採点を維持した検証済み対策はなく、テスト除外や課題差替えはしていません。[保留判断](../reports/terminal-bench-20261007/data/held-review.json)。

成功率の分母は57/モデル。保留をモデルの失敗として加算していません。subsetは実装・DB・運用寄りの選択で無作為標本ではなく、公式89課題スコアには外挿できません。3反復は同一課題の繰返しで、57の異なる課題を測ったことにはなりません。

## 同一ではない比較条件

| 時点 | 変更 | 解釈 |
| --- | --- | --- |
| 初期8採点後 | 全比較モデルのunload＋対象cache準備 | 初期8件とは起動前条件が違い、prepも欠測 |
| 36採点後 | 入力由来inlineゼロhex引用の限定例外v1 | 過去36件とは反復監視条件が違う |
| 99採点後 | polyglot-c-pyのagent導入だけHTTPS/公開CA | API以前の準備失敗から復旧 |
| 108採点後 | query-optimizeにも同じ導入対策 | 元課題・採点・導入timeoutは維持 |
| 141採点後 | hex160桁折返しの限定認識v2 | 過去141件とは反復監視条件が違う |

引用の上限512、1要求合計4096、入力user/tool由来、inlineコード限定、他の反復検知/SSE/資源ガードは維持。採点対象で引用例外が発動したAPIは0件です。実装が入力を正しく認識する証拠はCPUテスト/保存応答再生に限られます。後期ポリシーで過去の採点をやり直してはいません。

資源中断2件、引用ガード中断2件、agent導入中断2件は採点外。原本を保持し、レビュー後に対応する別ラベル1件ずつを採用しました。正常な不正解の改善目的の再試行はありません。公式時間切れ10件は成績に含め、提出物が成功した2件はreward1のまま保持しています。

## 速度・電力

- 初回TTFTはcoldモデル起動を含みます。warm常駐の速度と同一視できません。
- モデルの行動によりAPI回数・入力長・出力量が異なります。同一token列に対するkernel速度比較ではありません。
- Strata timingsとvLLM metricsのprefill定義、cache情報の取得可否が異なります。
- 1秒電力記録はHarbor生存中だけです。API drain・モデル解放/cache準備・oracle・試行間・採点外中断は総Whから欠けています。
- 公開値はGPU2枚のセンサー値で、全ホストのコンセント電力ではありません。

新メモリ準備以降163採点試行ではswap停止が再発せず、最大swap82.828MiBでした。ただし根本原因解決や無期限安定性の証明ではありません。詳細な定義は[計測方法](measurement.md)にあります。
